Find code in one step.

PeterGanuRusty (pgr) is a desktop command-line tool for AI coding agents, written in Rust. The agent asks it where a function is defined and what calls it, and gets the answer in one step. It works with any agent that can run a command.

It runs only on your own machine, with no account, no server and no network use. Measured under Claude Code. A smaller check under the Codex CLI showed no consistent saving (see Benchmarks).

Every turn re-reads everything

An agent works in turns, and on each turn it reads its whole conversation again. Every extra turn pays for the same context one more time.

Two turns is the floor for a lookup that needs a command: one to ask and one to answer. A pack in the prompt, with no command to call, takes the asking turn away; given the commands as well, agents still ran a lookup in 11 of 12 runs. A brief pack alone, without a lookup command took 1.0 turns per task on Claude Haiku 5.5 at low effort and the original questions. No index took 4.0. On the held-out questions it took 1.0 turns, and no index 4.7.

What it does for an agent

One call answers the question an agent asks most. The first capability is the one this site measures; the others are shown so you know what else the command does.

Finds definitions and callers in one call

An agent asks once and gets where a function is defined, its parameters and every function that calls it.

pgr about SomeFunction

Measured

Searches code by meaning

An agent describes a job in words and gets the function that does it.

pgr find "where tokens expire"

Not measured

Shows what a change touches

Before editing, an agent sees what depends on the code it is about to change.

pgr affected SomeFunction

Not measured

Remembers findings across sessions

What an agent has already worked out does not have to be found again next time. A finding is stored with pgr retain and read back with pgr recall.

pgr recall "how does login work"

Not measured

The study measures the first capability. One of its questions describes a job in words, but the runs do not show whether searching by meaning helps (see Limits on the Study page). The other capabilities are not covered by the measurements on this site.

Fully correct runs over both question sets

Across both question sets and both models, in these runs, one agent using "A brief pack alone, without a lookup command" was fully correct in 12 of 12 runs, against 10 of 11 with "Our engine, first generation, with embeddings". On the held-out questions alone, 6 of 6 against 4 of 5, though the held-out set is not held out for a round-six configuration.

Counted over four cells: Claude Haiku 5.5 at low effort and Claude Sonnet 5.5 at medium effort, on the original and the held-out questions. The held-out questions are a second set of three questions of the same three shapes, written later by the same team. The people and agents who built the engine through round five did not see them while building it. The pack of round six was written after these questions had been run, so for round six they are a second set of questions, not an untouched one. Round six ran on 2026-10-14, a day after round five. Its rows are set against their own baseline in the Round six chapter, except the highlighted one when it is a round-six row: its no-index figure is from round five.

"Most reliable" marks the one configuration with the highest share of fully correct runs over four cells (Claude Haiku 5.5 at low effort and Claude Sonnet 5.5 at medium effort, on the original and the held-out questions), a tie going to the lower mean tokens; only configurations run at least 3 times in each of those four cells, and so measured on both question sets, were eligible. The rule was set after the runs of rounds one to five were known and before round six ran.

What the rule picked, and what that means

The rule is the highest share of fully correct runs over four cells, then the fewest tokens. Six configurations were eligible and four of them were fully correct in every run of the four cells. A pack alone used the fewest tokens of those, so it is the one marked. The rule was written after round five and before round six ran. After it, in the rule's order, and averaged over the same four cells:

  • PGR, graph and search, with a brief pack12 of 12 fully correct, 155k tokens, 2.2 turns
  • PGR: graph and search12 of 12 fully correct, 157k tokens, 2.3 turns
  • PGR: code graph12 of 12 fully correct, 198k tokens, 2.9 turns
  • What a pack alone means for your own agents. The harness that starts the agent runs pgr pack on the task and puts the output in the agent's brief. The agent answers from it and calls no command and no tool. Making a pack used no language model: the program's own search found the matches, with its small neural table switched on. The agent made one call, with the pack in its prompt.
  • The questions suit it. The builders wrote them, and two of the three in each set name the function in backticks. A pack is built from the words of the question, so it finds such a function at once.
  • The held-out questions are not held out for it. The part of the pack that finds the functions a question names was written after the held-out questions had been run in round five. For this pick they are a second set of questions, not an untouched one.
  • It has not been tested on open-ended work. Nothing here asked an agent to find a bug, change code or explore a repository it was not pointed at. Where the pack misses what is needed, an agent with no command cannot look further.
  • The saving against no index crosses rounds. No index was last run in round five, a day earlier than round six. The same configuration run in both rounds started with a context 296 tokens larger in round six, 0.5% of that context.

How to read the numbers

Evidence
The results on this site come from one repository, a Python project: 172 runs of a single agent in 62 cells, three runs in most of them. The engine itself is written in Rust.
Tokens and turns
A token count is all the text the model read or wrote over a task, including the conversation it reads again on every turn, and a turn is one round trip to the model.
Models
The runs asked for a class of model: the smallest, a middle one and the largest. These are the models those classes meant on the days of rounds one to five, 2026-10-07 to 2026-10-14: Claude Haiku 5.5 at low effort, Claude Sonnet 5.5 at medium effort, Claude Opus 5.5 at maximum effort. Round six, on 2026-10-14, asked for the same classes; its records name only the model family, so its versions are taken to be the same.
Questions
The original questions are the three lookups used in every round; the held-out questions are a second set of three.

Teams of agents

Round six, run on 2026-10-14, put the engine in the setups a team of agents uses: 351 agents in 135 runs over 45 cells, three runs a cell. Each finding below sets two setups of this round against each other, on the same repository and the same question sets. The one comparison that crosses rounds is the highlighted configuration against no index, because the no-index agent was last run in round five, a day earlier; it is marked where it appears. The builders of the engine wrote the questions.

  • 70k to 71ktokens in one turn with a pack and no tool at all; fully correct in 12 of 12 runs
  • 27% to 32%fewer tokenswith a pack in the brief of each of three subagents; 12 of 12 runs fully correct
  • 14% to 34%more tokenswith the team hub on lookup work, and no accuracy gained
  • 15 of 15note fields right with the notes in the brief, against 0 of 15 with none; a demonstration set
  • 18 of 18runs fully correct with the tools in an Ubuntu virtual machine; on Windows 18 of 18
  • 4 of 6runs fully correct without the neural network, against 6 of 6 with it; both of the misses had a read altered by another tool, so the network is not shown to be the cause
  • −15% to +3%change in tokenswith three models in their roles, against Claude Opus 5.5 reviewing as well: fewer in three of four pairs, 3% more in the other; the runs of the two sides overlap in three of them; 24 of 24 runs fully correct

Three runs a cell cannot support a claim of significance. A difference of one turn between two setups is noise, and so is a difference of one fully correct run.

Another tool on the test machine, the one the Study page describes under the no-index control, was installed in round six as well. It altered a read in 11 of the round's 135 runs, and in 5 of the 11 runs that were not fully correct. A finding that rests on a pair with such a run says so, and gives the change without it. Running the round again with that tool off would settle it; that was not done.

The questions were written by the builders of the engine, and two of the three in each set name the function in backticks. That suits a pack, which is built from the words of the question. The third describes a job in words; the pack alone answered it too.

Size on disk

Sizes of the files on disk, summed per folder. The first generation is the set of separate tools the Rust engine replaces, as installed and used on the test machine; the Python interpreter itself is not counted. Its model, cache and index folders hold data for more than one repository, so they are listed apart from the programs. The index sizes are for the test repository (86 files, 68,316 lines). Sizes are in megabytes of a million bytes, the unit of the Install page. Measured 2026-10-13 on one Windows 11 laptop; the packed index of pgr 0.2.0 on 2026-10-14.

The index is what the engine builds once for a repository and reads on every lookup. The packed index of pgr 0.2.0 is 30% smaller than the one before, 8.5 MB to 5.9 MB, and lossless. The same test repository was indexed by pgr 0.2.0, with every index file written with a lossless codec (deflate, read back byte for byte). The 88 commands recorded from the benchmark and 53 pack and loadout outputs print exactly what they printed before; query times stay inside their targets.

Listed apart from the programs: the first generation's models, caches and index folders hold 619.9 MB, for a total of 1125.0 MB. The new program is 1 file. The model inside the program file was left uncompressed: the best lossless codec saved 14.7%, under the 15% bar, and would need a 32 MB copy beside the program.

The engine, pgr, is written in Rust, all of it. Python is around it, not inside it: the repository the benchmark asks questions about is a Python project, the first generation's tools, the benchmark harness and this site's generator are Python programs, and uv, pipx and pip are optional ways to deliver the same Rust program.

Round six: teams of agents

Round six, run on 2026-10-14, put the engine in the setups a team of agents uses: 351 agents in 135 runs over 45 cells, three runs a cell. Each finding below sets two setups of this round against each other, on the same repository and the same question sets. The one comparison that crosses rounds is the highlighted configuration against no index, because the no-index agent was last run in round five, a day earlier; it is marked where it appears. The builders of the engine wrote the questions.

What the rule picked, and what that means

The rule is the highest share of fully correct runs over four cells, then the fewest tokens. Six configurations were eligible and four of them were fully correct in every run of the four cells. A pack alone used the fewest tokens of those, so it is the one marked. The rule was written after round five and before round six ran. After it, in the rule's order, and averaged over the same four cells:

  • PGR, graph and search, with a brief pack12 of 12 fully correct, 155k tokens, 2.2 turns
  • PGR: graph and search12 of 12 fully correct, 157k tokens, 2.3 turns
  • PGR: code graph12 of 12 fully correct, 198k tokens, 2.9 turns
  • What a pack alone means for your own agents. The harness that starts the agent runs pgr pack on the task and puts the output in the agent's brief. The agent answers from it and calls no command and no tool. Making a pack used no language model: the program's own search found the matches, with its small neural table switched on. The agent made one call, with the pack in its prompt.
  • The questions suit it. The builders wrote them, and two of the three in each set name the function in backticks. A pack is built from the words of the question, so it finds such a function at once.
  • The held-out questions are not held out for it. The part of the pack that finds the functions a question names was written after the held-out questions had been run in round five. For this pick they are a second set of questions, not an untouched one.
  • It has not been tested on open-ended work. Nothing here asked an agent to find a bug, change code or explore a repository it was not pointed at. Where the pack misses what is needed, an agent with no command cannot look further.
  • The saving against no index crosses rounds. No index was last run in round five, a day earlier than round six. The same configuration run in both rounds started with a context 296 tokens larger in round six, 0.5% of that context.

A pack alone

With a pack in the prompt and no tool at all, one agent answered the three lookups in one turn on 70k to 71k tokens and was fully correct in 12 of 12 runs over four cells: Claude Haiku 5.5 and Claude Sonnet 5.5, on the original and the held-out questions. The baseline of the same round, one agent with the lookup command and no pack, needed 135k to 181k tokens over 2.0 to 2.7 turns on Claude Haiku 5.5, so on that model the pack alone used 48% to 61% fewer tokens. Another tool on the test machine altered a read in 1 of the 12 runs of these pairs; with those runs set aside the change would be 48% fewer (Claude Haiku 5.5 at low effort, original questions).

Packs in the briefs of three subagents

Three subagents started together, one question each, with nobody checking their answers (Claude Haiku 5.5): with a pack in each brief the three used 27% to 32% fewer tokens than without, and every answer was fully correct (12 of 12 runs, both ways). With an orchestrator (Claude Opus 5.5) that writes the briefs and checks the answers, the packs moved the total from 13% fewer to 1% more tokens (12 of 12 runs fully correct), and the runs of the two sides overlap. Another tool on the test machine altered a read in 1 of the 12 runs of these pairs; with those runs set aside the change would be 8% fewer (Claude Haiku 5.5 at low effort, original questions, with an orchestrator).

A pack and the commands together

One agent given the pack and the lookup commands as well, on Claude Haiku 5.5, used from 34% fewer to 42% more tokens than the same agent with no pack. Over its twelve runs, on both models and both question sets, it ran a lookup anyway in 11 and answered in one turn in 1: with commands in reach, the pack did not take the asking turn away. Another tool on the test machine altered a read in 1 of the 12 runs of these pairs; with those runs set aside the change would be 12% fewer (Claude Haiku 5.5 at low effort, original questions, one agent).

The team hub

On lookup work an orchestrated team (Claude Opus 5.5 orchestrating, Claude Haiku 5.5 answering) used 14% to 34% more tokens when its subagents filed what they found in the hub and the reviewer started from it, and gained no accuracy: 24 of 24 runs were fully correct, with the hub and without. Another tool on the test machine altered a read in 3 of the 24 runs of these pairs; with those runs set aside the change would be 36% more (Claude Haiku 5.5 at low effort, original questions, orchestrated); 36% more (Claude Haiku 5.5 at low effort, held-out questions, orchestrated). A small demonstration set, written by the builders so that each answer needs a note an earlier agent filed, shows what the hub is for: Claude Haiku 5.5 got 0 of 15 note fields right with no notes, 15 of 15 when it loaded the notes itself and 15 of 15 when the notes were put in its brief, the lowest mean of the three, though the runs of the three overlap: 163k tokens against 207k to load them and 206k with none.

The tools in a virtual machine

With the repository and the tools inside an Ubuntu virtual machine (WSL 2) and the agent outside it, 18 of 18 runs were fully correct, against 18 of 18 on Windows, and the mean tokens moved from 13% fewer to 9% more over six pairs, while the three runs of one cell differ from each other by up to 104%. Three runs a cell cannot support a claim of significance. A difference of one turn between two setups is noise, and so is a difference of one fully correct run.

Another tool on the test machine, the one the Study page describes under the no-index control, was installed in round six as well. It altered a read in 11 of the round's 135 runs, and in 5 of the 11 runs that were not fully correct. A finding that rests on a pair with such a run says so, and gives the change without it. Running the round again with that tool off would settle it; that was not done.

The questions were written by the builders of the engine, and two of the three in each set name the function in backticks. That suits a pack, which is built from the words of the question. The third describes a job in words; the pack alone answered it too.

None of this was tested on open-ended work: no bug to find, no change to make, no question that names no function and describes none.

The demonstration set was written to show one feature of the hub. It is not a test nobody tuned for.

The held-out questions are not held out for the packs of this round. The questions were written and committed before pgr 0.2.0, and the part of its pack that finds the functions a question names was written after them. For round six they are a second set of questions, not an untouched one.

The index is what the engine builds once for a repository and reads on every lookup. The packed index of pgr 0.2.0 is 30% smaller than the one before, 8.5 MB to 5.9 MB, and lossless. The same test repository was indexed by pgr 0.2.0, with every index file written with a lossless codec (deflate, read back byte for byte). The 88 commands recorded from the benchmark and 53 pack and loadout outputs print exactly what they printed before; query times stay inside their targets.

Listed apart from the programs: the first generation's models, caches and index folders hold 619.9 MB, for a total of 1125.0 MB. The new program is 1 file. The model inside the program file was left uncompressed: the best lossless codec saved 14.7%, under the 15% bar, and would need a 32 MB copy beside the program.

The engine, pgr, is written in Rust, all of it. Python is around it, not inside it: the repository the benchmark asks questions about is a Python project, the first generation's tools, the benchmark harness and this site's generator are Python programs, and uv, pipx and pip are optional ways to deliver the same Rust program.

Findings

In plain sentences, with their numbers.

  • On Claude Haiku 5.5 at low effort and the original questions, in these runs, one agent using "A brief pack alone, without a lookup command" needed 71k tokens and 1.0 turns for the three lookups, against 294k tokens and 4.0 turns with no index: 76% fewer tokens in this one cell. Across the four cells where both were measured, Claude Haiku 5.5 at low effort and Claude Sonnet 5.5 at medium effort on the original and the held-out questions, the saving against no index was 72% to 80% in tokens.
  • In these runs "A brief pack alone, without a lookup command" was fully correct in 3 of 3 runs on Claude Haiku 5.5 at low effort and the original questions, and "Our engine, first generation, with embeddings" in 3 of 3. Over the four cells where both were measured, 12 of 12 against 10 of 11. A run is fully correct when all three answers are. Fully correct counts are not set against no index: another tool on the test machine altered some of the no-index agent's reads, which lowered its correctness.
  • Two turns is the floor for a task that needs a lookup command: one to ask and one to answer. On the original questions "Our engine, first generation, with embeddings" took 2 turns on both classes, with 134k tokens on Claude Haiku 5.5 at low effort and 133k on Claude Sonnet 5.5 at medium effort. "A brief pack alone, without a lookup command" has no command to call: with the pack already in its prompt it answered in 1 turn on both classes, with 71k tokens on Claude Haiku 5.5 at low effort and 70k on Claude Sonnet 5.5 at medium effort. On the held-out questions "A brief pack alone, without a lookup command" took 1.0 turns on Claude Haiku 5.5 at low effort and 1.0 on Claude Sonnet 5.5 at medium effort, and "Our engine, first generation, with embeddings" 2.0 turns on Claude Haiku 5.5 at low effort and 4.0 on Claude Sonnet 5.5 at medium effort.
  • Tokens follow turns, because most of a run's tokens are the agent's start-up context, read again on every turn. On Claude Haiku 5.5 at low effort and the original questions the leanest published configuration, "A brief pack alone, without a lookup command", took 1.0 turns and 71k tokens, and the heaviest, "Two separate tools: code graph and semantic search", 7.0 turns and 480k tokens.
  • With no index, in these runs, one agent used 294k tokens on Claude Haiku 5.5 at low effort (3 runs) and 261k tokens on Claude Sonnet 5.5 at medium effort (3 runs) on the original questions. The larger model did not need far fewer tokens for the same lookups.

Memory

Memory that already held the answers, filled by a session that answered the same questions, matched the two-turn floor and did not beat it: "PGR: memory, filled with the answers" and "PGR: graph, search and memory, filled with the answers" took 2 turns on both classes and used 0.5k to 0.9k more tokens than graph and search without memory. That is a best case, since the memory held the answers. Memory filled by an earlier session that explored the repository without seeing any question, compared cell by cell with graph and search without memory, used fewer tokens in 1 of 4 cells and more in 3 of 4; it was fully correct in 11 of 12 runs, against 12 of 12 without memory. With three runs in a cell, differences of this size are inside the spread between repeats. These single lookups are not the task memory is for, and tasks that span sessions were not measured.

Orchestration

With a reviewing agent on top of three Claude Haiku 5.5 (low effort) workers, 84 of 84 runs ended fully correct, against 110 of 118 for one Claude Haiku 5.5 agent alone, on the held-out and original questions. The reviewing agent is of a larger model than the workers, so this compares more than orchestration. A run cost about 106 times as much. That is an estimate: a price list applied to the measured tokens, pooled over 40 configurations, and for 45 of 84 orchestrated runs the planning cost is itself estimated from the planning calls that were measured.

A tool that alters reads

A tool on the test machine that alters what an agent reads did not lower token use on these lookups (+2%, against 21% between repeats of one prompt). Without an index, 5 of 9 runs with it ended fully correct and 13 of 17 without it: too few runs to call that a clear effect. The same tool altered some of the no-index control's reads in the second session, which is why the control's correctness is not set against the others.

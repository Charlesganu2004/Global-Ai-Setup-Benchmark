Study

How the measurements were made, what they cover and what they leave out.

What was asked

  • 3questions in a set
  • 2question sets
  • 6questions in all

Three code-navigation questions, put to the agent in every run on the original set. Three more, of the same shapes, make up the held-out set below.

  • Who calls a functionName every function in the repository that calls a given function.
  • Where a function is definedGive the file and the line where a named function is defined, its parameter names and the functions that call it.
  • Which function does a jobGiven a described job, name the function that does it, say where it is defined and name its counterpart, the function that reverses it.

Question sets

The same three kinds of lookup, asked on two sets of questions.

  • Original questionsThe three questions above. Every round has used them, and the people who built the engine saw them while building it, so a result on them could reflect tuning to them.
  • Held-out questionsA second set of three questions of the same three shapes, written later by the same team. The people and agents who built the engine through round five did not see them while building it. The pack of round six was written after these questions had been run, so for round six they are a second set of questions, not an untouched one. It is not independent: the same team wrote both sets, on the same repository, in the same three shapes, and the job descriptions in the which-function questions follow the wording of the functions' own documentation. It checks whether the engine was fitted to the first three questions, not whether it works on other kinds of question. They were run on 14 configurations, on Claude Haiku 5.5 at low effort and Claude Sonnet 5.5 at medium effort, with 2 to 3 runs in each cell.

How answers were graded

Every answer was checked by a script against an answer key, and no score was given by a person judging an answer. The keys for the questions about callers and definitions were read from the repository's syntax tree; the key for the which-function question was written by hand. The authors reviewed all of them. For the which-function question on the held-out set, the key accepts either of two functions, because both do the job.

Each answer scores between 0 and 1, with partial credit: a list of callers scores by how many are named and how many are wrong. The mean score is the average of these scores. A run is fully correct when all three of its answers score full marks, so one missed caller is enough to make a run not fully correct.

Only one question separates the configurations in these runs: of the 26 published single-agent runs that were not fully correct, 20 missed part of the answer to "Who calls a function".

What each agent was told

Each configuration's agent was given a description of its own tool, so that it knew what the tool does and how to ask it. These descriptions differ in length and detail, and this was not controlled. The agent with no index was told which of its ordinary tools it could use and nothing more.

Every agent was also told that the task was a measurement of what a code lookup costs. A result therefore mixes the tool with how well it was described. The prompts are not shown on this site.

What a token count is

  • 99%of the tokens were cache reads or writes
  • 65.9ktokens of start-up context
  • 99%of the most reliable configuration's tokens were that context
  • What is countedThe tokens of a run are the input, the output and the cache reads and writes of the agent, added up over the whole task. 99% of the tokens counted in the 172 published single-agent runs were cache reads or writes.
  • Where they come fromAn agent starts with a context of about 65.9k tokens: the instructions, skills and tool descriptions of the test machine. Every turn reads it again. On Claude Haiku 5.5 at low effort with the original questions that context and the conversation read again on each turn made up 99% of the tokens of "A brief pack alone, without a lookup command" and 94% of those of the no-index agent.
  • What followsTokens and turns are therefore one measurement counted twice, and most of the saving shown here is the saving of turns: about 69k tokens for each turn avoided. The output of the lookups themselves is small beside that.
  • MoneyA token read from the cache costs less than one that is not, so a saving in tokens is not a saving in money of the same size. This site gives no money figures except the estimate in the orchestration finding.

Sessions and memory

  • 3sessions
  • 62.9k to 64.9ktokens of start-up context, earlier to later

What differs between the two sessions the results come from, and how the memory was filled.

  • Three sessionsThe results come from three sessions, the first a few days before the others. The first measured the earlier configurations. The second, round five, measured the second-generation engine and the held-out questions, and repeated three earlier configurations: no index and two builds of the first-generation engine. The leaderboard shows the repeats, which were measured on the same day as the second generation. The third, round six, ran on 2026-10-14, a day later, and measured the engine in team setups with its own baseline; the no-index agent was not run again, so the highlighted configuration, which comes from round six, is set against the no-index agent of round five. Three configurations from the first session were not repeated. They keep their first-session figures and are marked "Earlier session" on the leaderboard: Two separate tools: code graph and semantic search; Symbol index with embeddings; Read-compression tool. Their tokens are not directly comparable with the rest.
  • Start-up contextAn agent's start-up context, the text it reads before it sees a question, grew between the sessions. On Claude Haiku 5.5 at low effort and Claude Sonnet 5.5 at medium effort it averaged 62.9k tokens in the earlier runs of the three repeated configurations (23 agents) and 64.9k in their repeats (15 agents). Every turn reads it again, so the same configuration costs more tokens now than it did then. That is why the leaderboard compares runs made on the same day, with one exception: the highlighted configuration of round six against the no-index agent of round five, whose start-up contexts differ by 296 tokens (0.5%).
  • How the memory was filledSome configurations use a memory of earlier sessions. Before the runs, the memory was filled by one of two earlier sessions: one that answered the same questions the runs ask, and one that explored the repository without seeing any question. The first kind is a best case, because the memory already holds the answers, and the configurations that use it say so in their names. Neither is a test of the task memory is for: work that spans sessions was not measured.

Round six: teams of agents

  • 351agents in team setups
  • 135runs
  • 45cells, three runs each
  • What ran351 agents in 135 runs over 45 cells, on the same Python repository as every round and the same two sets of three questions, plus a small demonstration set. One agent answered all three questions on Claude Haiku 5.5 at low effort or Claude Sonnet 5.5 at medium effort; three subagents (Claude Haiku 5.5) were started together, one question each; an orchestrator (Claude Opus 5.5 at maximum effort) wrote their briefs and checked their answers. Each finding on the Benchmarks page is between two setups of this round; the one comparison across rounds is the highlighted configuration against no index.
  • A packA pack is what the program's pack command prints for a question: the definitions, callers and matching code it finds, up to a fixed size (730 to 755 tokens each in these runs, estimated at four bytes to a token). The harness made each pack before the agent started and put it in the prompt. Making a pack used no language model: the program's own search found the matches, with its small neural table switched on. A pack is part of the prompt, so the agent reads it again on every turn.
  • A pack aloneIn this setup the agent has the pack in its prompt and may call no command and no tool, and may say that a field is unknown. It measures whether the pack is enough by itself, and what an answer costs when it is not.
  • The team hubA shared bank of notes, kept by the program with no model and no server, built from the ideas of TencentCloud's TencentDB-Agent-Memory. Subagents file what they found; the reviewer starts from what was filed. A note says which roles filed it and how old it is, and is marked stale when the code it names has changed since.
  • The demonstration setThree questions written by the builders to show one feature of the hub: each needs one lookup and one note that an earlier agent filed. A decision with a ticket, a note that has gone stale, and a fact confirmed by two roles. The notes were filed before the runs. It is a demonstration, not a test nobody tuned for.
  • The virtual machineAn Ubuntu machine under WSL 2. The repository, the Linux build of the program, its index and the note banks are inside the machine and the agent stays outside it; code is printed from inside. Wall time is not compared, because it includes starting the machine for every call.
  • No neural networkThe program with its one neural part, the table that gives search its sense of meaning, switched off for the index and for every call. Search then works on words alone.
  • Three models, each in its roleClaude Opus 5.5 plans the work, Claude Haiku 5.5 does the lookups and Claude Sonnet 5.5 reviews the answers with the program's commands, against Claude Opus 5.5 doing the planning and the review.
  • Across roundsThe no-index control ran in round five. The same configuration run in both rounds started with a context 296 tokens larger in round six, so the saving of the highlighted configuration against no index crosses two rounds. The difference is 0.5% of that context.
  • Three runs a cell cannot support a claim of significance. A difference of one turn between two setups is noise, and so is a difference of one fully correct run.
  • Another tool on the test machine, the one the Study page describes under the no-index control, was installed in round six as well. It altered a read in 11 of the round's 135 runs, and in 5 of the 11 runs that were not fully correct. A finding that rests on a pair with such a run says so, and gives the change without it. Running the round again with that tool off would settle it; that was not done.
  • The questions were written by the builders of the engine, and two of the three in each set name the function in backticks. That suits a pack, which is built from the words of the question. The third describes a job in words; the pack alone answered it too.
  • None of this was tested on open-ended work: no bug to find, no change to make, no question that names no function and describes none.
  • The demonstration set was written to show one feature of the hub. It is not a test nobody tuned for.
  • The held-out questions are not held out for the packs of this round. The questions were written and committed before pgr 0.2.0, and the part of its pack that finds the functions a question names was written after them. For round six they are a second set of questions, not an untouched one.

The control

The no-index agent, and what happened to its reads on the test machine.

  • What happenedOn the test machine, another tool altered some of the lines the no-index agent read. In some runs it hid the very lines that show one of the callers the callers question asks for, so those agents left that caller out. That is a fact about the test machine, not about having no index.
  • How oftenIn the second session the tool acted on 11 of 11 no-index runs. Among the other published configurations it acted on PGR: code graph (8 of 12 runs); PGR: search (11 of 12 runs); PGR: search and memory, filled with the answers (5 of 6 runs), and on none of the runs of the other seven.
  • How often, round sixIn round six the tool acted in 48 of the round's 135 runs and altered a read in 11, among them 5 of the 11 runs that were not fully correct. The Benchmarks page gives each finding that rests on such a run with the change it would show without them.
  • The day's countsIn the second session the no-index agent was fully correct in 2 of 3 Claude Haiku 5.5 (low effort) runs and 0 of 3 Claude Sonnet 5.5 (medium effort) runs on the original questions, and in 3 of 3 Claude Haiku 5.5 (low effort) runs and 2 of 2 Claude Sonnet 5.5 (medium effort) runs on the held-out questions.
  • The earlier session's countsIn the first session, which had no such tool, it was fully correct in 4 of 5 Claude Haiku 5.5 (low effort) runs, 3 of 3 Claude Sonnet 5.5 (medium effort) runs and 3 of 3 Claude Opus 5.5 (maximum effort) runs.
  • Tokens in each sessionOn Claude Haiku 5.5 at low effort and the original questions the no-index agent used 365k tokens and 5.0 turns in the first session (5 runs) and 294k tokens and 4.0 turns in the second (3 runs). The second session's control used fewer tokens, so it is the less favourable one for the product on tokens.
  • Effect on tokensIn earlier tests of the same tool, token use changed by +2%, against 21% between repeats of one prompt.
  • What this site does about itThe no-index figures are shown as measured, with a note on the leaderboard. The product is set against no index on tokens and turns only. Fully correct runs and mean score are set only against the first-generation engine, which was measured on the same day on the same machine and which the tool did not act on. For the highlighted configuration of round six that comparison crosses a day: its runs were made on 2026-10-14, the first generation's the day before. Running the control again with that tool off, in the same session as the others, would remove the problem.

Limits

  • 1repository
  • 1language
  • 1 to 3runs in a cell
  • 6questions
  • One repositoryEvery result comes from one repository of 86 files, a Python project. Other repositories may behave differently.
  • One languageThe repository the questions were asked about is a Python project, and nothing here says how the configurations do on other languages. The engine itself is written in Rust; that is a separate matter from the language of the repository it is asked about.
  • Six questionsSix lookup questions of modest difficulty, in two sets of three. Only one question separates the configurations: of the 26 published single-agent runs that were not fully correct, 20 missed part of the answer to "Who calls a function". The "Which function does a job" question was fully answered in 166 of 172 runs, 23 of 23 of them by configurations without search, so these runs cannot show whether searching by meaning helps. Harder questions may separate the configurations more, or less.
  • Questions that suit the toolTwo of the three questions in each set ask for the callers of a function, which a lookup tool answers directly, and none was written to need the body of a function to be read. Questions about what a function does may come out differently.
  • A weak baselineThe no-index agent had only its own basic file search and file reading tools, and no command line. A stronger unaided baseline, such as an agent with a shell and a syntax-aware search, was not measured, so the savings shown are against this baseline only.
  • Few runs, one taskEach published cell holds 1 to 3 runs, and every run answers the same 3 questions, so the runs of a cell are repeats of one task, not samples of many. Three runs cannot support a claim of significance, and this site makes none. A difference of one run or one turn is inside the run-to-run spread. In the 57 published cells with at least two runs, the highest run used 26% more tokens than the lowest at the median and 215% more at most, and in 23 of them at least half as many again. One turn is about 69k tokens. In 11 cells some runs were fully correct and some were not. For "A brief pack alone, without a lookup command", the lowest and highest run in each of its four cells were: Claude Haiku 5.5 at low effort, original questions, 71k to 71k; Claude Sonnet 5.5 at medium effort, original questions, 70k to 70k; Claude Haiku 5.5 at low effort, held-out questions, 71k to 71k; Claude Sonnet 5.5 at medium effort, held-out questions, 70k to 70k.
  • Unequal instructionsEach configuration's agent was given a description of its own tool. The descriptions differ in length and detail, and this was not controlled. See What each agent was told.
  • The same teamThe same team built the engine, wrote both question sets and ran the study.
  • Start-up contextAn agent starts with about 65.9k tokens of context from the test machine: its instructions, skills and tools. On another machine each turn costs a different number of tokens, and so does the saving.
  • Machine loadWall time depends on what else the test machine was doing. Token counts do not.
  • Cost figuresWhere a run is said to cost a multiple of another, the cost is an estimate: a price list typed into the analysis and applied to the measured tokens, not read from a bill.

Search without a neural network

Challenges made from five code bases, with no model and no human labels: the query is the words of a commit subject, and the right answer is a file that commit changed; the commit-subject challenges come from four of the code bases. Three variants of the search are scored on the same challenges, held-out half. Intervals are 95% from 2,000 resamples of the challenges.

VariantRecall at 1Recall at 5Mean reciprocal rank
Both together, the default61.5%55.4% to 68.1%90.6%86.4% to 94.4%0.7310.685 to 0.780
Words only, no neural network61.5%55.4% to 68.1%93.0%89.2% to 96.2%0.7550.712 to 0.800
Meaning only, with embeddings57.8%51.2% to 64.8%80.3%75.1% to 85.5%0.6780.626 to 0.732

Paired difference against the default, on the same challenges:

  • Words only, no neural network, against both together, the default: recall at 1 +0.0 points (interval -5.2 to +5.2, includes zero); recall at 5 +2.4 points (interval +0.0 to +4.7, includes zero); mean reciprocal rank +0.024 (interval -0.009 to +0.057, includes zero).
  • Meaning only, with embeddings, against both together, the default: recall at 1 -3.8 points (interval -8.5 to +0.9, includes zero); recall at 5 -10.3 points (interval -15.5 to -5.6, excludes zero); mean reciprocal rank -0.053 (interval -0.089 to -0.020, excludes zero).

The test-name challenges are too few to settle anything: 25 held-out queries pooled over all the code bases. For the default variant their recall at 1 is 24.0% with an interval of 8.0% to 40.0%, wide enough to hold every variant. They are reported and not interpreted.

  • The queries come from developer-written test names and commit subjects, not from questions an agent would ask.
  • In three of the code bases a single file is the answer to 40 to 53% of the commit-subject challenges, so credit piles up on that file.
  • Credit for a commit subject is file-level and lenient: any hit in a changed file counts.
  • There are five code bases in three languages. One of them has no named tests, so it is judged on commit subjects alone.
  • The default variant was built by people who had seen none of these challenges, and the figures here are the held-out half.
  • Pooled rows weight each challenge equally, so the larger code bases count more.
  • A test-name query and its answer share words by construction. The numbers compare variants; they are not a forecast of agent behaviour.
  • Credit by cover matching goes to a block that contains the function, so a variant that returns coarser blocks gains from it. The data file keeps the exact-matching numbers beside the main ones for that reason.
  • Answers in example, documentation, compatibility and legacy folders are left out, because the engine demotes most of them on purpose. A change to that policy is not measured here.
  • A variant whose weights were searched with the tuning tool was searched on the tune half only and is judged here on the held-out half. The tune half holds few test-name challenges and a few hundred commit-subject challenges, so a tuned variant can fit it and gain nothing held out.

A second agent program

  • Agent program and modelThe Codex CLI with gpt-6-astra at medium effort. Run on 12 sessions.
  • What was runThree sessions in each of four cells: no index and pgr, on the original and on the held-out questions. One agent answers all three questions in a session.
  • How it came outShowed no consistent saving. On the original questions the sessions with pgr, against those with no index, used 37.5% fewer tokens, on the held-out questions 15.4% more. Every session was fully correct.
  • What it does not coverOther models, other efforts, other repositories and other agent programs. Orchestration, subagents and the memory.
  • Why its counts stand aloneThe Codex CLI counts tokens its own way, with its own instructions, tools and caching. Only the two methods inside this check can be compared with each other; the counts are not comparable with the Claude Code counts.

What is not on this site

The prompts and the settings of the agents and the names of the other tools are not on this site.

The benchmark pages report measured outcomes: counts of tokens, turns and answers, and what is not measured is marked. It names what each configuration can do (look up definitions and callers, search, remember), not how the others do it.

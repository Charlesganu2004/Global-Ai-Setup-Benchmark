Study

How the measurements were made, what they cover and what they leave out.

What was asked

Three code-navigation questions, put to the agent in every run on the original set. Three more, of the same shapes, make up the held-out set below.

  • Who calls a functionName every function in the repository that calls a given function.
  • Where a function is definedGive the file and the line where a named function is defined, its parameter names and the functions that call it.
  • Which function does a jobGiven a described job, name the function that does it, say where it is defined and name its counterpart, the function that reverses it.

Question sets

The same three kinds of lookup, asked on two sets of questions.

  • Original questionsThe three questions above. Every round has used them, and the people who built the engine saw them while building it, so a result on them could reflect tuning to them.
  • Held-out questionsThree more lookups of the same three shapes, written after the engine was built and never seen by the people or agents who built it. They exist to check that the engine was not fitted to the first set. They were run on six configurations, on the light and mid classes, with 2 to 3 runs in each cell.

How answers were graded

Every answer was checked by a script against facts read from the repository's syntax tree, so no score depends on a person's judgement.

Each answer scores between 0 and 1. The share of answers correct is the average score. A run is fully correct when all three of its answers score full marks.

How much was run

  • RepositoryPython, 86 files, about 68,000 lines
  • Questions3 in each of 2 sets, each asked in every run on its set
  • Agents884
  • Runs499
  • Configurations tested44, of which 14 are published here
  • Runs per configuration and class1 to 6

Three ways of organising the agents were tried. Only the first feeds the leaderboard and the chart.

  • Setup 1One agent answering all three questions.
  • Setup 2Three agents, one question each, with nobody checking their answers.
  • Setup 3One agent that briefs three workers and checks what they return.

Model classes

Three classes of model, named only by size. Model names and versions are not given.

  • LightThe smallest model class, run at low reasoning effort.
  • MidA middle model class, run at medium reasoning effort.
  • TopThe largest model class, run at the highest reasoning effort.

Sessions, memory and the control

What differs between the two sessions the results come from, and what to keep in mind about the control.

  • Two sessionsThe results come from two sessions a few days apart. The first measured the earlier configurations. The second measured the second-generation engine and the held-out questions, and repeated three earlier configurations: no index and two builds of the first-generation engine. The leaderboard shows the repeats, so every configuration compared with the engine was measured on the same day. The earlier runs of those three are not shown here. Three configurations from the first session were not repeated and keep their first-session figures: Two separate tools: code graph and semantic search; Symbol index with embeddings; Read-compression tool.
  • Start-up contextAn agent's start-up context, the text it reads before it sees a question, grew between the sessions. On the light and mid classes it averaged 62.9k tokens in the earlier runs of the three repeated configurations (23 agents) and 64.9k in their repeats (15 agents). Every turn reads it again, so the same configuration costs more tokens now than it did then. That is why the leaderboard compares runs made on the same day.
  • How the memory was filledSome configurations use a memory of earlier sessions. Before the runs, the memory was filled by one of two earlier sessions: one that answered the same questions the runs ask, and one that explored the repository without seeing any question. The first kind is a best case, because the memory already holds the answers. Neither is a test of the task memory is for: work that spans sessions was not measured.
  • The controlOn the test machine, the control's file reads pass through a read-compression tool, which hid lines the control needed in some runs. In the second session the control was fully correct in 2 of 3 light-class runs and 0 of 3 mid-class runs on the original questions, and in 3 of 3 light-class runs and 2 of 2 mid-class runs on the held-out questions. In the first session, which had no such tool, it was fully correct in 4 of 5 light-class runs, 3 of 3 mid-class runs and 3 of 3 top-class runs.

Limits

  • One repositoryEvery result comes from one Python repository of 86 files. Other repositories may behave differently.
  • One languagePython only. Nothing here says how the configurations do on other languages.
  • Six questionsSix lookup questions of modest difficulty, in two sets of three. Harder questions may separate the configurations more, or less.
  • Small run countsEach configuration and class was run between 1 and 6 times. A cell with one run is an example, not an average, and a difference of one turn is inside the noise.
  • Three runs per cellThe second session ran each cell three times, and two of its 33 cells hold two complete runs. With three runs, a difference of one fully correct run is inside the noise.
  • Machine loadWall time depends on what else the test machine was doing. Token counts do not.
  • Cost figuresWhere a run is said to cost a multiple of another, the cost is list prices applied to the measured tokens.

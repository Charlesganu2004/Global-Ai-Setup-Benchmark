Study

How the measurements were made, what they cover and what they leave out.

What was asked

Three code-navigation questions, put to the agent in every run on the original set. Three more, of the same shapes, make up the held-out set below.

  • Who calls a functionName every function in the repository that calls a given function.
  • Where a function is definedGive the file and the line where a named function is defined, its parameter names and the functions that call it.
  • Which function does a jobGiven a described job, name the function that does it, say where it is defined and name its counterpart, the function that reverses it.

Question sets

The same three kinds of lookup, asked on two sets of questions.

  • Original questionsThe three questions above. Every round has used them, and the people who built the engine saw them while building it, so a result on them could reflect tuning to them.
  • Held-out questionsA second set of three questions of the same three shapes, written later by the same team. The people and agents who built the engine did not see them while building it. It is not independent: the same team wrote both sets, on the same repository, in the same three shapes, and the job descriptions in the which-function questions follow the wording of the functions' own documentation. It checks whether the engine was fitted to the first three questions, not whether it works on other kinds of question. They were run on six configurations, on the light and mid classes, with 2 to 3 runs in each cell.

How answers were graded

Every answer was checked by a script against an answer key, and no score was given by a person judging an answer. The keys for the questions about callers and definitions were read from the repository's syntax tree; the key for the which-function question was written by hand. The authors reviewed all of them. For the which-function question on the held-out set, the key accepts either of two functions, because both do the job.

Each answer scores between 0 and 1, with partial credit: a list of callers scores by how many are named and how many are wrong. The mean score is the average of these scores. A run is fully correct when all three of its answers score full marks, so one missed caller is enough to make a run not fully correct.

Only one question separates the configurations in these runs: of the 18 published single-agent runs that were not fully correct, 15 missed part of the answer to "Who calls a function".

What each agent was told

Each configuration's agent was given a description of its own tool, so that it knew what the tool does and how to ask it. These descriptions differ in length and detail, and this was not controlled. The agent with no index was told which of its ordinary tools it could use and nothing more.

Every agent was also told that the task was a measurement of what a code lookup costs. A result therefore mixes the tool with how well it was described. The prompts are not published.

How much was run

  • RepositoryPython, 86 files, about 68,000 lines
  • Questions3 in each of 2 sets, each asked in every run on its set
  • Runs per published cell1 to 3
  • Runs behind the leaderboard112 single-agent runs in 42 cells: 5 cells of 1 run; 4 cells of 2 runs; 33 cells of 3 runs.
  • Agents and runs in all884 agents and 499 runs, which also count configurations that are not published, tests of another tool and setups with several agents. They show effort, not the sample behind a result.
  • Configurations44 were tested and 14 are published here. The authors chose which to publish; no rule did. Ten of the 25 unpublished configurations run at least 3 times on the light class and the original questions also took 2 turns with every run fully correct. Those runs are from the first session, when the start-up context was 3% smaller, so their tokens are not directly comparable.

Three ways of organising the agents were tried. Only the first feeds the leaderboard and the chart.

  • Setup 1One agent answering all three questions.
  • Setup 2Three agents, one question each, with nobody checking their answers.
  • Setup 3One agent that briefs three workers and checks what they return.

What a token count is

  • What is countedThe tokens of a run are the input, the output and the cache reads and writes of the agent, added up over the whole task. 99% of the tokens counted in the 112 published single-agent runs were cache reads or writes.
  • Where they come fromAn agent starts with a context of about 64.7k tokens: the instructions, skills and tool descriptions of the test machine. Every turn reads it again. On the light class with the original questions that context made up 97% of the tokens of "PGR: graph and search" and 94% of those of the no-index agent.
  • What followsTokens and turns are therefore one measurement counted twice, and most of the saving shown here is the saving of turns: about 69k tokens for each turn avoided. The output of the lookups themselves is small beside that.
  • MoneyA token read from the cache costs less than one that is not, so a saving in tokens is not a saving in money of the same size. This site gives no money figures except the estimate in the orchestration finding.

Model classes

Three classes of model, named only by size. Model names and versions are not given.

  • LightThe smallest model class, run at low reasoning effort.
  • MidA middle model class, run at medium reasoning effort.
  • TopThe largest model class, run at the highest reasoning effort.

Sessions and memory

What differs between the two sessions the results come from, and how the memory was filled.

  • Two sessionsThe results come from two sessions a few days apart. The first measured the earlier configurations. The second measured the second-generation engine and the held-out questions, and repeated three earlier configurations: no index and two builds of the first-generation engine. The leaderboard shows the repeats, which were measured on the same day as the second generation. Three configurations from the first session were not repeated. They keep their first-session figures and are marked "Earlier session" on the leaderboard: Two separate tools: code graph and semantic search; Symbol index with embeddings; Read-compression tool. Their tokens are not directly comparable with the rest.
  • Start-up contextAn agent's start-up context, the text it reads before it sees a question, grew between the sessions. On the light and mid classes it averaged 62.9k tokens in the earlier runs of the three repeated configurations (23 agents) and 64.9k in their repeats (15 agents). Every turn reads it again, so the same configuration costs more tokens now than it did then. That is why the leaderboard compares runs made on the same day.
  • How the memory was filledSome configurations use a memory of earlier sessions. Before the runs, the memory was filled by one of two earlier sessions: one that answered the same questions the runs ask, and one that explored the repository without seeing any question. The first kind is a best case, because the memory already holds the answers, and the configurations that use it say so in their names. Neither is a test of the task memory is for: work that spans sessions was not measured.

The control

The no-index agent, and what happened to its reads on the test machine.

  • What happenedOn the test machine, another tool altered some of the lines the no-index agent read. In some runs it hid the very lines that show one of the callers the callers question asks for, so those agents left that caller out. That is a fact about the test machine, not about having no index.
  • How oftenIn the second session the tool acted on 11 of 11 no-index runs. Among the other published configurations it acted on PGR: code graph (8 of 12 runs); PGR: search (11 of 12 runs); PGR: search and memory, filled with the answers (5 of 6 runs), and on none of the runs of the other seven, among them "PGR: graph and search".
  • The day's countsIn the second session the no-index agent was fully correct in 2 of 3 light-class runs and 0 of 3 mid-class runs on the original questions, and in 3 of 3 light-class runs and 2 of 2 mid-class runs on the held-out questions.
  • The earlier session's countsIn the first session, which had no such tool, it was fully correct in 4 of 5 light-class runs, 3 of 3 mid-class runs and 3 of 3 top-class runs.
  • Tokens in each sessionOn the light class and the original questions the no-index agent used 365k tokens and 5.0 turns in the first session (5 runs) and 294k tokens and 4.0 turns in the second (3 runs). The second session's control used fewer tokens, so it is the less favourable one for the product on tokens.
  • Effect on tokensIn earlier tests of the same tool, token use changed by +2%, against 21% between repeats of one prompt.
  • What this site does about itThe no-index figures are shown as measured, with a note on the leaderboard. The product is set against no index on tokens and turns only. Fully correct runs and mean score are set only against the first-generation engine, which was measured on the same day on the same machine and which the tool did not act on. Running the control again with that tool off, in the same session as the others, would remove the problem.

Limits

  • One repositoryEvery result comes from one Python repository of 86 files. Other repositories may behave differently.
  • One languagePython only. Nothing here says how the configurations do on other languages.
  • Six questionsSix lookup questions of modest difficulty, in two sets of three. Only one question separates the configurations: of the 18 published single-agent runs that were not fully correct, 15 missed part of the answer to "Who calls a function". The "Which function does a job" question was fully answered in 110 of 112 runs, 23 of 23 of them by configurations without search, so these runs cannot show whether searching by meaning helps. Harder questions may separate the configurations more, or less.
  • Questions that suit the toolTwo of the three questions in each set ask for the callers of a function, which a lookup tool answers directly, and none was written to need the body of a function to be read. Questions about what a function does may come out differently.
  • A weak baselineThe no-index agent had only its own basic file search and file reading tools, and no command line. A stronger unaided baseline, such as an agent with a shell and a syntax-aware search, was not measured, so the savings shown are against this baseline only.
  • Few runs, one taskEach published cell holds 1 to 3 runs, and every run answers the same 3 questions, so the runs of a cell are repeats of one task, not samples of many. Three runs cannot support a claim of significance, and this site makes none. A difference of one run or one turn is inside the run-to-run spread. In the 37 published cells with at least two runs, the highest run used 1% more tokens than the lowest at the median and 215% more at most, and in 11 of them at least half as many again. One turn is about 69k tokens. In 7 cells some runs were fully correct and some were not. For "PGR: graph and search", the lowest and highest run in each of its four cells were: light class, original questions, 134k to 134k; mid class, original questions, 133k to 133k; light class, held-out questions, 134k to 274k; mid class, held-out questions, 134k to 204k.
  • Unequal instructionsEach configuration's agent was given a description of its own tool. The descriptions differ in length and detail, and this was not controlled. See What each agent was told.
  • The same teamThe same team built the engine, wrote both question sets and ran the study.
  • Start-up contextAn agent starts with about 64.7k tokens of context from the test machine: its instructions, skills and tools. On another machine each turn costs a different number of tokens, and so does the saving.
  • Machine loadWall time depends on what else the test machine was doing. Token counts do not.
  • Cost figuresWhere a run is said to cost a multiple of another, the cost is an estimate: a price list typed into the analysis and applied to the measured tokens, not read from a bill.

What is not published

Implementation details are not published.

This site reports measured outcomes only: counts of tokens, turns and answers. It names what each configuration can do (look up definitions and callers, search, remember), not how it does it, and it does not publish the prompts or settings of the agents.

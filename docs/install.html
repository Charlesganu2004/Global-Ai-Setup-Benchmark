Install pgr

PeterGanuRusty (pgr) is a desktop command-line tool for AI coding agents, for Windows, macOS and Linux. It works with any agent that can run a command, and it is written in Rust. Measured under Claude Code. A smaller check under the Codex CLI showed no consistent saving (see Benchmarks). One paste installs it.

What the installer does

  1. It downloads one program file

    The file for your system and its checksum list, SHA256SUMS.txt, from the release at https://github.com/Charlesganu2004/Global-Ai-Setup-Benchmark/releases/latest. Nothing else is downloaded: no Python, no runtime, no packages.

  2. It checks the file

    The installer compares the file with its published SHA-256. If they differ, it stops and nothing is installed.

  3. It puts the file in a folder of your user account

    On Windows that is %LOCALAPPDATA%\Programs\pgr\pgr.exe, and the folder is added to your user PATH, so open a new terminal afterwards. On macOS and Linux it is ~/.local/bin/pgr; if that folder is not on your PATH, the installer prints the line to add. No administrator rights and no root are used.

  4. It runs the program once

    The installer asks the new file for its version, so a file that cannot run on your system is reported at once.

Your first three commands

Open a terminal inside a git repository. Replace SomeFunction with a name from your code.

  1. Build the index of the repository you are in. Run it once, and again after the code changes.

    pgr refresh

  2. Ask two questions in one call: where SomeFunction is defined and what calls it (use a name from your code), and which code does a job you can only describe.

    pgr ask about:SomeFunction "find:where tokens expire"

  3. Every command, with what it prints.

    pgr help

Tell your agent to use it

An agent uses the command when its instructions say so. Paste these four lines into the instruction file your agent reads at the start of a session.

Before reading files to find where something is, run pgr ask.
For a name, run pgr ask about:NAME: the definition, the callers and what it calls.
For a job you cannot name, run pgr ask "find:what the code does".
Open a file only for the lines the answer names.
Not part of the measured benchmark

The program also runs as a Model Context Protocol server, for agents that speak the protocol instead of running commands. Start it with the command below. The benchmark on this site measured agents that ran commands, not this route.

pgr mcp

Use it in a team of agents

The pattern round six supports, in four steps. Each step says what was measured and what is advice that follows from it. The questions were written by the builders of the engine and none of this was tested on open-ended work.

  1. Run pgr pack on each subagent's task and paste the output into its brief

    Measured In round six the harness made a pack for each question before the agent started and put it in the prompt. Making a pack used no language model: the program's own search found the matches, with its small neural table switched on. Three subagents started together used 27% to 32% fewer tokens with a pack in each brief than without, and 12 of 12 runs were fully correct.

    Advice Give the command the task in the words you would give a colleague: a pack is built from the words it is given. Make one pack for each subagent's own task, not one for the whole job.

  2. Tell it to answer from the pack, and to look up only what is missing

    Measured Each pack came with the note that it may be all the agent needs and that anything it does not show can be looked up. Even so, an agent that also had the lookup commands ran one in 11 of 12 runs and answered in one turn in 1 of 12. An agent with the pack and no command answered in one turn on 70k to 71k tokens, fully correct in 12 of 12 runs.

    Advice Say it plainly in the brief, and keep the lookup command within reach for any work that is open-ended: an agent with no command cannot look further, and round six did not test open-ended work.

  3. Give the reviewer the same packs

    Measured In the orchestrated runs the reviewer got the same packs as the subagents, and the total moved from 13% fewer to 1% more tokens against runs with no packs (12 of 12 runs fully correct), inside the spread of three runs. What the reviewer's packs are worth alone was not isolated.

    Advice A reviewer that starts from the packs can spend its calls on checking what the subagents said instead of finding it again.

  4. Use the hub only for findings that cannot be looked up again

    Measured On lookup work the hub used 14% to 34% more tokens and gained no accuracy: 24 of 24 runs were fully correct, with the hub and without. On a demonstration set whose answers are notes an earlier agent left, an agent got 0 of 15 note fields right with no notes and 15 of 15 with the notes in its brief, at the lowest mean tokens of the three setups, though the runs of the three overlap.

    Advice File a decision, a ticket number, a reason, or a finding someone confirmed. Do not file what pgr ask answers again. pgr handoff files a note and pgr loadout reads what was filed for a task; pgr help lists their options.

What was tested, and what was not

What ran

  • The Windows installer, on Windows 11, from the public release, followed by a first index build and a query in a new repository.
  • The shell installer, on Ubuntu, from the public release, with the same first index build and query.
  • Installing the wheel with pip, on both of those systems.
  • The build workflow installed and ran the Windows, Linux x86-64 and macOS Apple-silicon builds.

What did not run

  • The Linux ARM64 and the macOS Intel builds were cross-compiled and checked, not run.
  • The Linux builds need the GNU C library, so Alpine (musl) is not covered yet.

Checked 2026-10-13.

Test suites

  • Windows 11 (development machine): the engine's whole test suite. 729 passed, 0 failed, 5 ignored.
  • Ubuntu 24.04 on WSL 2 (the same machine): the engine's whole test suite, built natively. 654 passed, 0 failed, 5 ignored on the 0.1 source after one fix; the first run found a test that failed in 23 of 40 runs on Linux only, fixed (0 of 40 after).
  • Linux, macOS, Windows (GitHub's build machines): the engine's whole test suite on every push that touches the engine. passed on all three for 0.1 and for 0.2.

Same answers on different systems

  • The Windows build against the Linux build, the Linux one run inside Ubuntu, on the same repository: 56 of 56 commands gave byte-identical output (42 recorded from the benchmark's agents, 14 added), for 0.1 and for 0.2.
  • The 0.2 Windows build against the binary the fifth round measured: 88 of 88 recorded commands gave identical output.

The installers, run from the public release

  • Windows 11: install.ps1 from the public release, then a first index and a query in a new repository: passed.
  • Ubuntu 24.04 on WSL 2: install.sh from the public release, then a first index and a query in a new repository: passed.
  • both: installing the wheel from the release with pip: passed.

Built but not run here

  • Linux aarch64 (cross-compiled, checked, not run)
  • macOS Intel (cross-compiled, checked, not run)
